  - app/services/stats.py:25-28 counts only tasks where task.status == 
    TaskStatus.COMPLETED ("completed"). Task 1 holds "done", so completed = 0
    and completion_rate = 0.0.
  - app/services/stats.py:31-34 has a second effect: the overdue check also
    compares against COMPLETED. A task finished through /complete that has a
    past due date is still counted as overdue.

  3. GET /tasks?status=completed
  - app/routes/tasks.py:11-15 passes status="completed" to list_tasks().
  - app/services/tasks.py:66-73 _validate_status accepts the value, and
    filter_by(status="completed") does an exact match. That doesn't match
    "done", so the result is [].

  Root cause

  app/models.py:8-17 defines two values that mean "finished":
  - COMPLETED = "completed" is the current, canonical value.
  - DONE = "done" is a legacy value from the old mobile client. It's kept only
    "so old rows still validate".

  complete_task writes the legacy value, but every reader (stats, overdue,
  status filter) only looks for the canonical value. It's a one-word bug in one
  service function, with the other code paths working as designed.

  Proposed fix

  Main fix (one line): in app/services/tasks.py, change complete_task to write
  TaskStatus.COMPLETED. New completions will then show up in stats and in the
  status filter, and stop counting as overdue.

  Tasks already stored with "done": the one-line fix does nothing for them.
  Every task completed before the fix, and any task the old mobile client sets
  to "done" through PATCH, would still be missing from stats and from
  ?status=completed, and would still count as overdue. There are two ways to
  handle them, and I'd do both:

  1. One-off data migration: run UPDATE task SET status = 'completed' WHERE 
     status = 'done';. The repo has no migrations folder (no Alembic), so this
     would be a small script or a manual SQL step against the real database.
     Tests use a fresh in-memory database, so they aren't affected.
  2. Convert "done" on write: in _validate_status, change DONE to COMPLETED
     before saving. The old mobile client can keep sending "done", but it never
     reaches the database. Keep DONE in TaskStatus.ALL so those requests still
     validate.

  A read-side alternative is to make stats and list_tasks treat {COMPLETED, 
  DONE} as finished. It works without touching data, but every future query
  would have to remember both values, which is how this bug happened. I'd skip
  it.

● For this repo as it stands, no. You only need the script if a real database
  somewhere already has "done" rows in it.

  Why the code fix doesn't cover old rows: the fix only changes values as
  they're written or queried. A row that already holds "done" stays that way,
  and the app still handles it wrongly:
  - /stats doesn't count it as completed, and still counts it as overdue if its
    due date has passed.
  - ?status=completed doesn't return it.
  - ?status=done doesn't return it either, because that filter is now converted
    to "completed". So those rows can't be found through the status filter at
    all.

  Why you don't need it here: I looked and there's no database file in the
  project. There's no tasks.db and no instance/ folder. The app creates tasks.db
  on first run, and every row it writes now goes through the fix, so it can
  never hold "done". The tests use a fresh in-memory database each time.

  When you would need it: if you run the app against a database that was used
  before this fix, such as an existing tasks.db or whatever DATABASE_URL points
  to. Any task completed through /complete, or set to "done" by the old mobile
  client, would have the old value. Run the script once on that database and
  you're done. Running it again just updates 0 rows.

  If this project has no real deployment with old data, which seems likely for a
  Week 9 drill, you can delete scripts/. If you'd rather keep it, it's a small
  record of how to fix old data. Do you want me to remove it before committing?
